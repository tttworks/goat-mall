## 环境

### 1. 本机访问 GitHub 必须走 VPN 代理
- 现象：`git ls-remote github.com` 卡死/无输出
- 解法：仓库本地配置 `git config http.proxy http://127.0.0.1:2080`（goat-mall 已配置；凭据走 Windows 凭据管理器缓存）
- 验证：`git ls-remote origin` 有返回即通

### 2. 本机 Chrome 无头不可用（RDP + GPU 环境）
- 现象：Chrome 152/156 无头启动即退出，无输出
- 解法：需要浏览器自动化时用 **Edge 无头 + CDP**（`msedge.exe --headless=new --remote-debugging-port=9222`）+ playwright-core `connectOverCDP`
- 关联：mmacg 嗅探即此路线；`D:/#工作文档/02.合作伙伴/GreatestOfAllToyz/.crawl/crawl.js` 可复用

## 服务器与商务

### 4. BitsFlow 新机默认仅公钥认证，密码登录被拒
- 现象：面板给的 root 密码登录报 `server sent: publickey`（sshd 只收公钥）
- 根因：BitsFlow / VirtFusion 面板「SSH 方式」开关只对**重装系统时**生效，运行中的 sshd 不改
- 解法：重装系统时选「密码」方式，或面板 Console 进去做 `sed -i 's/^#*PasswordAuthentication.*/PasswordAuthentication yes/' /etc/ssh/sshd_config && systemctl restart ssh`；我们走重装（空盘零损失）拿到密码通道，并追加专用 ed25519 公钥
- 验证：专用密钥 + 密码双通道登录成功

### 5. Debian 13（Trixie）装宝塔前必须补编译依赖
- 现象：纯净 Trixie 缺 gcc / make / python3-dev / libssl-dev 等，宝塔编译安装 Nginx / 软件会失败
- 解法：安装前 `apt-get install -y gcc g++ make python3-dev libssl-dev zlib1g-dev ...`（完整清单见 install 命令）；依赖齐备后 `bash install_panel.sh` 编译通过
- 验证：依赖齐备后编译安装无 `文件不存在 / 编译失败`
- 关联：PHP 7.x 在 Debian 13 不被支持（我们不用 PHP-FPM，无关）；宝塔稳定版 10.x 可适配 Debian 13

### 6. 域名归属 ≠ 许可证归属 ≠ 备案归属（商务坑）
- 现象：客户说「许可证上有这个域名」，但 whois 显示该域名已易主
- 根因：增值电信许可证 = 公司主体 + 载明网站两栏；证有效性跟公司走（津B2-20220260 仍有效），但「载明网站」栏登记的原域名已不属于客户
- 解法：优先买回原域名（许可证一字不改）；否则新域名需重新备案 + 许可证域名变更（天津通管局，10-30 工作日）
- 验证：天眼查核证证号业务种类 + CNNIC whois 核证域名现持有人（注册人 / 邮箱 / 到期日）

### 7. Mercari 采集必须用日本归属 IP（地域风控）
- 现象：Mercari / Cloudflare 对大陆 IP 直接 403（Cf-Mitigated: challenge）
- 解法：采集机固定部署日本机房；BitsFlow 套餐页标注「香港IP」但实测我们这台是东京归属（216.23.x 段，与 #19 同池）——下单前务必查 IP 归属，香港池不能当采集机
- 验证：ip-api 查 216.23.112.40 = 日本东京涩谷 ✅

### 8. Debian 13 上 Redis 8 启动失败：jemalloc 的 mmap 被 MemoryDenyWriteExecute 拦截
- 现象：`systemctl start redis-server` 报 `error while loading shared libraries: libjemalloc.so.2: failed to map segment from shared object`（exit 127，连 ping 都空）；但前台手动 `redis-server --port 6390` 却能正常起（"Ready to accept connections"）
- 根因：Debian 13 的 redis systemd 单元默认带 `MemoryDenyWriteExecute=true`（激进加固），禁止 `PROT_EXEC` 内存映射；而 loader 加载 `libjemalloc.so.2` 时需要 exec 映射 → 被拒。叠加安装脚本误把**调试版 jemalloc** 装进 `/usr/local/lib` 盖住了系统包（ld.so 优先取 /usr/local/lib）
- 解法：① `rm -f /usr/local/lib/libjemalloc.so* && ldconfig`（让系统包 `/usr/lib/x86_64-linux-gnu/libjemalloc.so.2` 生效）；② 写 override `/etc/systemd/system/redis-server.service.d/override.conf` 设 `MemoryDenyWriteExecute=false`；③ `sysctl -w vm.overcommit_memory=1` 并落 `/etc/sysctl.d/99-goat.conf` 持久化（redis 官方推荐）
- 验证：`systemctl restart redis-server` → active；`redis-cli -a $REDPW ping` 回 `PONG`

### 9. Meilisearch 启动报 Permission denied (os error 13)：CWD 不可读导致读 ./config.toml 失败
- 现象：`systemctl start meilisearch` 立即失败，日志只有 `error=Permission denied (os error 13)`；strace 抓到 `openat(AT_FDCWD, "./config.toml", O_RDONLY) = -1 EACCES`
- 根因：meili 启动会在**当前工作目录**找 `./config.toml`。systemd 默认 CWD=`/`，但服务以 `meili` 用户跑、对根目录的 open 在某些环境下被拒（sudo 手动跑时 CWD=/root 同理）——只要 CWD 是 meili 读不了的地方就 EACCES。文件不存在本应 ENOENT，但目录不可读直接 EACCES
- 解法：unit 显式加 `WorkingDirectory=/var/lib/meili`（meili 拥有、可写）；该 open 即返回 ENOENT，meili 正常改用 CLI 参数。二进制从 GitHub release 直下 `meilisearch-linux-amd64`（v1.56.1，357MB），`/usr/local/bin/meilisearch`，systemd 托管 `--db-path /var/lib/meili/data --env production --master-key $MEILIKEY --no-analytics --http-addr 127.0.0.1:7700`
- 验证：`systemctl is-active meilisearch` = active；`curl 127.0.0.1:7700/health` 回 `{"status":"available"}`

### 10. overcommit / sysctl 持久化路径：Debian 13 没有 /etc/sysctl.conf
- 现象：往 `/etc/sysctl.conf` 追写入 sysctl 参数报 "No such file or directory"
- 解法：改写到 `/etc/sysctl.d/99-goat.conf`（Debian 13 采用 sysctl.d 片段机制），`sysctl --system` 或重启生效

### 11. Windows 本机装 PHP 跑 Laravel 测试：pcntl / posix 只能靠忽略
- 现象：`composer install` 连续报 `laravel/horizon requires ext-pcntl`、`ext-posix`，装不下去
- 根因：Horizon 依赖 POSIX 进程模型，Windows 版 PHP 根本没有这两个扩展（不是没开，是没有）
- 解法：`composer install --ignore-platform-req=ext-pcntl --ignore-platform-req=ext-posix`；生产 Linux 正常安装不受影响。**不要**写进 `composer.json` 的 `config.platform`——那会让生产环境缺扩展也能装成功，把问题推迟到运行时
- 验证：`php artisan test` → `Tests: 36 passed (158 assertions)`

### 12. SQLite 不回填数据库默认值：新建对象的枚举字段读出来是 null
- 现象：`Attempt to read property "value" on null`，只在测试环境（SQLite 内存库）出现，生产 PG 正常
- 根因：PostgreSQL 走 `INSERT ... RETURNING` 会把所有列回填给模型；SQLite 只回填自增主键。所以「payload 不传、靠库 default 兜底」的字段，新建对象上就是 `null`
- 解法：业务层显式补默认值再落库（`$payload['status'] ??= FigureStatus::Draft->value`），出参永不依赖数据库默认值
- 推广：凡是「建表给了 default + 创建后立刻读出来返回」的字段，都要显式赋值，否则只有换库时才炸

### 13. 纯数字 slug 与自增 id 撞空间 → 详情页永久 404
- 现象：商品名「初音未来 交响乐 1/7」，`Str::slug` 把中文剥掉后只剩 `17`；详情页 `/figures/17` 命中「数字优先按 id 查」的分支，查不到 → 404
- 根因：同一个路径参数兼职两种标识（id 与 slug），而 slug 生成规则允许产出纯数字
- 解法：① 生成侧纯数字一律加前缀（`figure-17`）；② 查询侧数字串同时匹配 slug 与 id，兼容历史数据
- 推广：商品 / 店铺 / 文章这类「可读标识 + 主键」共用路径参数的场景都要按这条防

### 14. Laravel 测试进程内 Auth guard 缓存 → 「已注销仍 200」的假失败
- 现象：`logout` 成功后立即用同一 token 请求 `/me`，仍返回 200
- 根因：同一个测试方法内复用同一个 app 实例，`RequestGuard` 缓存了首次解析出来的 user，第二个请求不再查库
- 解法：请求之间加 `$this->app['auth']->forgetGuards();`。真实 HTTP 每个请求独立进程，不存在该问题，所以这是测试写法问题而非产品缺陷
- 判据：断言失败但手工用 curl 复现不出来，先怀疑 guard 缓存

### 15. Symfony 头表的值是数组：直接 `(string)` 强转会抛 Array to string conversion
- 现象：支付通道验签时 `(string) $headers['x-payment-signature']` 直接报错，回调 500
- 根因：`$request->headers->all()` 返回 `array<string, array<int, string>>`（同名头可重复），不是 `array<string, string>`
- 解法：统一走取值 helper——`is_array($v) ? ($v[0] ?? '') : $v` 再 `trim()`；签名比对用 `hash_equals`（防时序侧信道）
- 推广：任何接收 `headers->all()` 的第三方适配层（微信 / 支付宝 / 对象存储回调）都要先归一化

### 16. `Accept: */*` 让未登录请求返回 500 而不是 401
- 现象：不带头调 `POST /api/v1/posts/media`，返回 500「Route [login] not defined」；带 `Accept: application/json` 就正常 401
- 根因：`ForceJson` 只在「完全没有 Accept 头」时才补 JSON；浏览器 / uni-app 的 XHR 会自动带 `Accept: */*`，此时 `expectsJson()` 为 false，`AuthenticationException` 走 web 分支 `redirect()->guest(route('login'))`，而 API 站点没有 login 路由
- 解法：改成按协商判断 `if (! $request->wantsJson()) { $request->headers->set('Accept', 'application/json'); }`，API 组内一律 JSON
- 判据：所有「未登录 → 401」的断言都要用不带 Accept 的原始请求再测一遍；只测 `postJson` 会漏掉这条

### 17. 公开路由里 `$request->user()` 永远是 null：想看「当前登录用户」得点名 sanctum guard
- 现象：帖子详情 / feed 都输出 `liked`，但登录用户看自己的点赞状态始终是 `false`
- 根因：公开路由没有 `auth:sanctum` 中间件，默认 guard 不会去解析 Bearer token，`$request->user()` 返回 null（而不是「解析失败」）
- 解法：`$request->user('sanctum')?->user_id` —— 显式点名 guard，有 token 就解析、没 token 就是 null，公开与登录公用同一个端点
- 副作用：测试里 `Sanctum::actingAs($author)` 之后请求详情会命中「作者可见自己待审帖」分支，原本断言 404 的用例必须换一个身份再测，否则测的是作者视角还以为是「他人视角」
- 推广：凡「公开可见 + 个性化字段」的端点（收藏态、点赞态、已读态）都用这个写法，别再为它单独挂鉴权中间件
